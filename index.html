TL;DR

  1. 三个维度：“从单用户 Agent 到多用户云服务”沿三个相互独立的维度展开：面向开发者的开放平台线（厂商云端接管 Agent 的哪些职责，L1–L5）、面向最终用户的产品形态线（对话型 → 任务型 → 常驻型，F1–F3），以及部署形态（A 专属常驻计算机 / B 每会话沙箱 / C 本机执行）；纵向上，一个 Agent 服务由沙箱、Harness、托管 Runtime、Orchestrator、Service 与协作治理层组成，L1–L5 的差别即厂商托管了其中哪几层（各层开源与商业产品见第 ⑩ 节）。两条线由“先自用，后外供”连接：厂商先在第一方任务型产品中验证 harness，再开放为托管服务（如 Codex 云端 → Agents API、WorkBuddy → WorkBuddy Managed Agents）。
  2. 开放平台线：三阶段螺旋式演进，终点趋同。2023–2024 年以黑盒方式托管会话（OpenAI Assistants、百炼、扣子、智谱智能体中心），因难以定制已逐步退出（Assistants 于 2026-08-26 关停）；2025 年 harness 以开源 SDK / CLI 形式开放；2025–2026 年托管回归，架构升级为“控制面与执行面（沙箱）分离”。2026 年 4–9 月，Anthropic、Google、腾讯（WorkBuddy Managed Agents）、智谱、火山方舟、OpenAI、阿里百炼先后推出 Managed Agents 类服务，其中 5 家明确采用 Agent / Environment / Session / Events 四要素模型，Google 以等价模型实现。
  3. 产品形态线：从任务型走向常驻型。任务型产品（Operator、Codex 云端、Jules、扣子空间等）自 2025-01 起出现。常驻型的判定标准是长期存在的主体由“任务”变为“Agent 实例”，仅增加定时触发不构成常驻型。常驻型分三波：自托管开源（OpenClaw，2025-11 首发、2026-01-30 定名；Hermes Agent）→ 云托管开源（腾讯云 Lighthouse 一键部署、Kimi Claw、ArkClaw 等，2026-01 起）→ 厂商自研数字员工（Gemini Spark、Grok Bot、Meta Muse、OpenAI dots 等，2026-05 起），后者增加了独立邮箱与电话、多渠道主动触达与无人值守执行规则。常驻型的出现不以 L5 为前提。
  4. 部署与多租户：五项改造，三种形态并存。会话状态移出进程、每会话独立沙箱（容器 → microVM / gVisor）、凭证不进沙箱、以预热池与快照休眠实现弹性、为 Agent 配置身份并实施治理。A、B、C 三种部署形态在 2026 年同时存在：其中“本机执行 ＋ 远程接入”（C）于 2026 年 2–9 月由 9 家中的 8 家推出官方方案（即内网穿透的产品化形态），是单用户 Agent 面向多端使用时改造成本最低的形态，其中继与配对能力可在 L5 的自托管沙箱中复用。
  5. 对独立 Agent 平台厂商（不自建大模型，聚焦 Harness 层）：最适配的基础设施是云厂商的模型无关 Runtime（火山 AgentKit、阿里 AgentRun / AgentBay、Google Agent Runtime）；内部接口宜按四要素模型设计；常驻型宜按“每 Agent 独立工作区与凭证作用域”设计隔离，避免“每用户一台共享计算机”带来的 Agent 间越权风险（见第 ④ 节 Grok Bot 案例）。
通俗理解：原有 Agent 只能运行在个人电脑上，关机即中断，且权限与该电脑相同。完成上述演进后，企业可以像开通云盘账号一样，为每位员工开通相互隔离、按用量计费、可 7×24 运行的 Agent，并可随时追溯其使用的身份与执行记录。

维度之间相互独立

同一产品形态可以采用不同的部署形态，例如：

  • 常驻型 × A：Grok Bot、Meta Muse（每用户一台），OpenAI dots（每 Agent 一台）
  • 常驻型 × C：OpenClaw、Hermes Agent（运行于用户自有设备）
  • 任务型 × B：Codex 云端、Jules（每任务一个临时环境）
  • 任务型 × A：AutoGLM 2.0（每用户一台云手机 / 云电脑）

多 Agent 能力分属两层

单个 Agent 内部的子 Agent、Handoff、扇出（如 Kimi Agent Swarm）属于 Harness 层；多个独立 Agent 组成团队并统一调度、授权与核算成本，属于 协作与治理层。阿里 AgentTeams 官方定位为“多智能体治理与协作平台”，采用 Leader-Worker 模型，可在同一团队中纳管 OpenClaw、Claude Code 等不同引擎，并明确不替代 Agent 运行时。

Serverless 的位置

Serverless 主要体现在 Service 层的计费与运维方式（按会话时长计费、免运维）。函数计算（FaaS，Function as a Service）以事件触发、按次调用为主（天翼云官方说明）；单个函数最长可执行 24 小时（官方常见问题），但函数不保持常驻进程。需要保持长连接与内存状态的交互式 Agent 会话，通常运行于 Serverless 容器或安全容器之中；函数计算适合承担事件处理、定时触发等环节。

托管服务、API 与 Managed Agents

API 是接口，即通过 HTTP 创建会话、发送消息、订阅事件流；托管服务（Service）是厂商运营的多租户服务本身，负责资源模型（Agent / Environment / Session / Events）、租户与配额、生命周期、计量计费与 SLA，API 是其对外入口；Managed Agents 是产品形态，即托管服务连同其下的编排、Runtime、沙箱与 Harness 整体交付，对应开放平台线的 L5。

“Runtime”一词的三种用法：同名、不同层

三种用法指三样不同的东西，而非同一事物的三个特征：它们可以同时出现在同一套系统中，各占一层。例如，腾讯 Octop Harness（③）基于 deepagents 构建，deepagents 运行于 LangGraph（②）之上，整体又可部署到 AgentCore Runtime（①）。三者同名，是因为都承担一部分“运行期”职责，即让 Agent 持续运行并管理运行中的状态，但管理的范围不同。

用法相对 Harness 的位置管理的范围典型
① 托管运行时（本页的“托管 Runtime”，云厂商通行用法）之上进程外、跨机器：部署、每会话隔离、弹性伸缩、会话状态服务AWS AgentCore Runtime、Vertex AI Agent Engine、阿里 AgentRun
② 持久执行运行时（LangChain 的定义）之下单条执行流（一次工作流或图的执行）：检查点、断点续跑、人工介入LangGraph、Temporal、Inngest
③ 进程内运行时库即 Harness 层在一个进程中注册并运行多个相互隔离的 Agent，每个有各自的模型、工具、记忆与 LangGraph 检查点；不涉及多用户并发与跨进程扩展腾讯 Octop Harness：自称“agent runtime”，以 AgentManager 管理进程内的多个 Agent，最终委托 deepagents 的 create_deep_agent 构建（README）

① 与 ② 都能“恢复”，但粒度不同：② 恢复到执行流中的某一步（检查点），① 恢复整个会话（事件日志与快照）。③ 中的“多个 Agent”指多个不同配置的 Agent（如不同的助手），而非多个用户同时运行；托管 Runtime 中的Harness 实例则是无状态进程，以会话租约同时承载多个用户的会话，会话状态在外部事件日志中，因此可水平扩展。选型或交流时，需先确认对方所说的 Runtime 指哪一种。

从单体 Harness 到托管服务：六步改造与两类协议

Managed Agents 的第一代把会话、harness 与沙箱放在同一个容器中，即单体形态：容器成了不可替换的“宠物”，故障即丢失会话。把一个单体 Harness 改造为 Managed Agents 式的托管服务，可拆为以下六步，每一步解决上一步遗留的问题。

与上方技术栈分层的对应（见“对应分层”一列）：①② 在 Harness 层内完成；③ 构成托管 Runtime 的核心；④ 对应沙箱 / 执行环境；⑤ 对应 Orchestrator；⑥ 对应托管服务（Service）。由此也可看出托管 Runtime的构成：② 的服务化接口 ＋ ③ 的无状态实例与外置会话状态，再加上每会话隔离、伸缩、身份与计量，并经 ④ 的 Executor Protocol 连接沙箱。远程接入不属于上云主线，作为旁路单列一行。

会话状态的位置随改造推进：进程内存（①）→ 本机事件文件（②③ 的本地形态）→ 外部会话事件日志 ＋ 工作区快照（③ 的云端形态）。改造完成后，Harness 实例本身不再保存会话状态。

从无状态到有状态：状态的三次迁移

① 模型 API 本身无状态，每次请求都要带上完整上下文；② Harness 把上下文保存在进程内存中，形成有状态的会话，但状态随进程存亡，且只服务一个用户；③ 托管 Runtime 把状态移出进程：harness 实例重新变为无状态，会话状态由外部存储承担，因此任意实例都能接续任意会话，可水平扩缩，单个实例故障也不丢会话。

有状态服务由哪几样组成

① 会话事件日志：只追加地记录每件事，重放即可重建上下文，是会话状态的唯一权威来源；② 工作区快照：保存沙箱中的文件系统结果，沙箱回收后可恢复；③ 会话租约：同一会话同一时刻只由一个实例处理，实例故障后租约过期，由其他实例接续；④ 记忆库与凭证保险库：跨会话的记忆，以及不进入沙箱的凭证。

Runtime 不等于 JSON-RPC

Codex App Server 这类本地运行时已具备“运行 Agent 循环 ＋ JSON-RPC 接口 ＋ 本机持久化”，JSON-RPC 只是它的对外接口。托管 Runtime 在此基础上增加的是平台能力：状态外置、每会话隔离、调度与伸缩、身份与配额、可观测与计量。沙箱是并列的执行面，由托管 Runtime 调度和连接，而不是包含在其中。

Orchestrator 与控制面、执行面的关系

Orchestrator 属于控制面，但不运行 Agent 循环。它负责“装配”：为会话准备好 Harness 实例与沙箱并把两者接上。会话开始后，模型调用与工具调用由 Harness 经两类协议完成，Orchestrator 只在分配、休眠、恢复与故障转移时介入。Anthropic 的做法中，沙箱由 harness 经工具调用按需创建。托管产品通常把这一层内嵌在 Runtime 或 Service 中。

同一抽象，运行方不同

接口代际描述调用方一次请求能得到什么；开放平台线描述由谁运行、由谁承担运维。mcp-agent 与 Responses API 处于同一代：调用方一次调用即可完成多轮工具调用，区别在于前者运行于开发者自己的进程，后者由厂商运营。云厂商若把此类开源实现部署为多租户服务，对其客户即构成 L3 级服务；把开源 Agent 服务端（如 OpenHands Agent Server）部署为多租户服务，则对应 L5。端云工具可以在一次请求中组合，但执行位置分处服务端与本地两侧：内置工具与远程 MCP 由服务端调用，自定义函数回到调用方执行；本地 MCP 经隧道接入时，由服务端发起调用，仍在本地执行。

接口代际与托管路线的关系

二者是同一演进的两个侧面，并非两条独立的线：L1、L3、L5 的产品本身即对应代际的接口。L4 托管 Runtime 由云厂商主导，提供的是部署与运行能力，不改变模型调用接口。2026 年，模型厂商的第 3 代接口与云厂商的托管 Runtime 在“Agent / Environment / Session / Events”四要素模型上汇合（见下文“与直觉路径的对照”中的路线分岔）。

第 3 代接口的交付形态

第 3 代产品均以 API 形式提供：调用方通过 HTTPS 以 JSON 格式创建 Agent、Environment 与 Session 并发送事件，再经 SSE（服务器推送事件流）接收执行过程；官方 SDK 与控制台是对同一套 API 的封装。以 Claude Managed Agents 为例，所有接口须携带 Beta 请求头；因会话状态保存在服务端，暂不适用零数据留存。具体调用步骤见四要素模型中的“调用示意”。

⑤ 风险与需要改造的部分

  1. 默认按本地可信环境设计：官方安全声明要求在公网或局域网部署时另加认证网关、IP 白名单与网络隔离。
  2. 沙箱隔离强度：AIO Sandbox 是普通容器，官方示例关闭了 seccomp；provisioner 未提供 RuntimeClass 配置；Kubernetes 1.36 起可用内置准入策略（MutatingAdmissionPolicy）按沙箱标签注入 RuntimeClass、节点选择与容忍，接入 gVisor 或 Kata 均无需修改代码。
  3. 宿主机目录挂载：provisioner 默认以 hostPath 挂载技能与用户数据，须改用 PVC（SKILLS_PVC_NAME、USERDATA_PVC_NAME）；多个沙箱 Pod 共享用户数据卷需要 ReadWriteMany 存储，需确认所用云盘或文件存储是否支持。
  4. provisioner 尚未完成的能力：按超时自动清理沙箱、NetworkPolicy 模板、按沙箱设置资源均在路线图中未完成，需自行补齐。
  5. 治理能力：无组织层级与按用户配额；RBAC 默认关闭；通用工具审批未见说明。
  6. 版本节奏：2.0 于 2026-06 发布、2.1 于 2026-09 发布，迭代频繁；默认沙箱镜像使用 latest 标签，须同步到自有镜像仓库并锁定版本。

与直觉路径的对照

一种常见的直觉是把开放平台线理解为线性的四个阶段。实际情况与之在终点和主要维度上一致，但在时间顺序、路线分岔上有明显差异。

直觉中的线性路径

  1. SDK，无状态服务
  2. 同一 Session / Response 的 API 服务
  3. 包装成 Agent Runtime
  4. 做成 Service

另外两个维度：安全（沙箱）、云上动态扩缩容

实际演进路径（按时间顺序）

✔ 一致终点是托管服务；安全隔离、弹性扩缩是贯穿始终的两条主轴。

↺ 顺序不同托管会话（2023）早于官方开源 SDK（2025）。早期托管以黑盒 Thread 和低代码 Bot 为主，因灵活性不足逐步退出：Assistants 于 2026-08-26 关停，Agent Builder 将于 2026-11-30 下线。

↑ 架构升级新一轮托管是“解耦式托管”：harness（控制面）和沙箱（执行面）分开，会话状态放在进程外，还可以接入自己的沙箱。

⑂ 路线分岔Runtime 和 Service 是两条并行路线：云厂（Google、火山、阿里、AWS）先建设模型无关的 Runtime；模型厂（OpenAI、Anthropic、智谱）直接将自家 harness 封装为 API 服务。2026 年两条路线在同一套接口上汇合。此外，“本机执行 ＋ 远程接入”（C 形态）作为接入形态独立发展：执行环境不变，仅将操作入口延伸至移动端，与上云主线并行发展。

→ 推动力各家第一方任务型 Agent 产品（Codex、Jules、扣子空间、AutoGLM 2.0、OK Computer、Claude Code 云会话、各家 OpenClaw 云托管产品）是基础设施的试验场：先内部验证，再对外提供。

各阶段定义

④ 产品形态线：从对话到常驻

产品形态线描述最终用户使用的 Agent 形态。各形态的根本区别在于长期存在的主体：对话型是一段对话；任务型是一个任务及其执行环境，交付后结束；常驻型是 Agent 实例本身，任务由其派生。

形态长期存在的主体由谁发起身份工作环境代表
F1 对话型对话线程用户逐轮输入代表用户平台内置沙箱，随对话存在ChatGPT、豆包、Kimi、智谱清言
F2 任务型任务，交付后结束用户派发任务代表用户（委托令牌）每任务一个临时环境为主Codex 云端、Jules、ChatGPT agent、扣子空间、OK Computer
F2 变体：定时 / 事件任务任务，按计划或事件重复发起定时器或事件代表用户每次运行一个临时环境Managed Agents 的定时运行、扣子 Agent Plan
F3 常驻型Agent 实例，跨任务持续存在定时、事件，或 Agent 依据目标自主发起独立身份（IM 机器人、邮箱、电话、钱包）持久工作区或专属计算机OpenClaw、Kimi Claw、Gemini Spark、Grok Bot、OpenAI dots

常驻型判定：须同时满足三项：① 实例与工作环境跨任务持续存在并保有记忆；② 拥有独立身份，而非仅以用户的委托令牌行事；③ 能主动发起（定时、事件或目标驱动），并经对外渠道触达用户。仅增加定时触发的任务属于“定时 / 事件任务”，不构成常驻型。

⑤ 部署形态与多租户改造

单用户 Agent（如 Claude Code、Codex CLI、OpenClaw）的默认设计前提是：单进程、单机、单用户，且权限与用户本人等同。向多用户云服务演进的过程中，各厂商均完成了以下五项关键改造。

C 形态的定义

C 形态的技术机制：内网穿透的产品化

用户电脑通常位于 NAT 或防火墙之后，没有公网地址。各家方案的共同做法是由本机主动向厂商中继建立出站连接，手机端指令经中继转发至本机执行，从而无需开放端口或配置 VPN。

开源远程接入项目的演进

开源项目先于厂商补位；官方 Remote Control 陆续推出后，单纯的远程接入被覆盖，开源项目转向更上层的能力。

⑧ 先后顺序验证：共同规律与例外

按每家进入各阶段的最早日期排序，开放平台线与产品形态线分行展示。开放平台线的共同规律是：L1（2023–24）→ L2 / L3（2025 上半年）→ L4（2025）→ L5（2026）；产品形态线为：F2 任务型（2025-01 起）→ F3 常驻型（自托管 2025-11 起，云托管 2026-01 起，厂商自研 2026-05 起）。两条线相互独立，常驻型的出现不以 L5 为前提。

例外与分岔

  • Anthropic 未经历平台托管阶段：Messages API 始终保持无状态，2025-05 才引入服务端工具；也未推出独立 Runtime 产品，仅提供自托管指南，随后直接推出 Managed Agents。
  • Google 的 Runtime 早于自家 SDK：Reasoning Engine 2024 年预览，2025-03 GA，而 ADK 于 2025-04、Interactions API 于 2025-12 才发布。这是云厂商的典型路径：先建设托管运行时，再完善开发框架。
  • DeepSeek 截至 2026-09 未提供托管 Runtime 或托管 Agent API；Kimi 于 2026-09-10 推出面向合作伙伴的 Agent 运行底座 Kimi Hosted Agents，技术细节尚未公开。Kimi 此前的 Formula 只托管“工具执行”；DeepSeek 2026-08-13 才开源自家 harness，上云依赖火山 AgentKit、国家超算互联网等第三方承接。
  • 常驻型不以 L5 为前提：Kimi Claw（2026-02）早于 Kimi Hosted Agents（2026-09）；Google Gemini Spark 与其Managed Agents 服务同日发布（2026-05-19）；xAI、Meta、Manus 在本调研范围内未见 L5 Managed Agents 服务，即直接推出常驻型产品；OpenClaw、Hermes Agent 等自托管常驻 Agent 在开放平台线上仍处于 L2。
  • 纯模型厂商的过渡策略是兼容现有 harness：智谱 GLM-4.5（2025-07）、DeepSeek（2025-08）都兼容 Anthropic 协议，让 Claude Code 这类现成 harness 直接驱动自家模型，之后再研发自有 harness。

⑪ 对独立 Agent 平台厂商的启示

独立 Agent 平台厂商，指独立于大模型厂商、不自建大模型，通过集成第三方模型提供 Agent Harness 及其多用户云服务的企业。下图参考架构提炼自 9 家厂商 2026 年的共性设计：控制面承载 harness 与会话状态，执行面承载可随时回收的沙箱，模型经统一网关接入、可按需替换。

按技术栈分层的选型要点

  • Harness：自研或采用开源 harness（Claude Agent SDK、OpenAI Agents SDK、deepagents、AgentScope、DeerFlow 等）。厂商的 Managed Agents（OpenAI、Anthropic、智谱等）仅支持自家模型；如需接入第三方模型，宜采用“开源或自研 harness ＋ 模型无关 Runtime”。
  • 托管 Runtime 与沙箱：可选云厂商的模型无关底座：火山 AgentKit、阿里 AgentRun ＋ 无影 AgentBay、Google Agent Runtime、腾讯云 Agent Runtime、AWS AgentCore；也可自建，例如 K8s 上的 agent-sandbox、E2B 或腾讯开源的 Cube Sandbox。
  • Orchestrator：以 Kubernetes ＋ 沙箱预热池承担会话调度与生命周期，事件驱动的多步编排可选 Temporal 等持久执行引擎。
  • 托管服务：内部接口按 Agent / Environment / Session / Events 设计，未来切换至任一托管服务时迁移成本较低；腾讯 WorkBuddy → WMA 表明，桌面 Agent 的内核可直接复用为云端托管服务的内核。
  • 快速起步：如需先行上线，可从接近成品的开源项目起步：云端多用户服务（WorkBuddy 类）首选评估 DeerFlow 2.x，常驻型可选 QwenPaw Hub 或 Octop，任务型可选 Omnigent 或 OpenHands，多 Agent 协作可选 AgentTeams，对话门户可选 LibreChat，对外 API 可参照 Omnara。
  • 常驻形态：自托管常驻 Agent（OpenClaw、Hermes Agent、Octop）运行在用户自备设备上，平台提供本地版与远程接入即可；云端托管常驻 Agent（F3 第二、三波）需要平台提供持久工作区、触发调度、渠道网关与独立身份，可在 B 形态沙箱底座上扩展，并按“每 Agent 独立工作区与凭证作用域”设计隔离。

安全与弹性基线（各厂商的共同实践）

  • 每个会话一个独立沙箱（最低是容器，正式环境用 gVisor 或 microVM），租户之间不共享进程。
  • 默认断网或只放行白名单出口；凭证由代理或保险库注入，不放进沙箱。
  • 为每个 Agent 配置独立身份，工具调用统一经网关鉴权与审计。
  • 预热池负责冷启动，空闲时快照休眠；按会话时长或 vCPU 秒计量。
  • 试点阶段可先采用 C 形态（本机执行 + 远程接入）或 A 形态（专属常驻计算机），正式服务采用 B 形态；C 形态所建设的中继、配对与审批能力可在 B 形态的自托管沙箱中复用。

提示：以上是对调研结论的归纳，不是对某个具体产品的推荐；选型前要按企业自身的模型清单、合规要求（数据驻留、ZDR）和规模开展 PoC。注意：Claude Managed Agents、OpenAI Agents API 目前都不支持 ZDR，OpenAI Agents API 的数据驻留目前只有美国。
